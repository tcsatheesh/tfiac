# Feature Specification: 008 — Windows VM Engine (jump box)

**Feature Branch**: `008-winvm`

**Created**: 2026-06-05

**Status**: Draft

**Input**: User description: "stand up a Windows VM in the sp01 dev resource
group" — a private, Bastion-only Windows jump box used to reach private
endpoints (RDP in, test private endpoints, test private DNS). Chosen
architecture: a **new dedicated engine** (`modules/winvm/` + `terraform/winvm/`)
parameterized 100% via tfvars + backend state key, deploying NOTHING by itself.
Each concrete deployment is a separate instance feature (e.g.
`105-sp01-dev-winvm`).

## Summary

Deploys a **single Windows x64 virtual machine** ("jump box") into an
**existing** resource group and an **existing** spoke subnet, with **no public
IP** (reachable only via the hub Azure Bastion). The local administrator
password is **generated by Terraform** (`random_password`) and stored as a
secret in an **existing Key Vault** — it is never placed in tfvars, code, or
plan output. Day-to-day login is via **Microsoft Entra ID over Bastion** (the
`AADLoginForWindows` extension); the Key Vault secret is break-glass only. The
VM carries a system-assigned managed identity, host encryption, secure boot,
and vTPM, and ships diagnostics to the shared hub Log Analytics workspace.

This is an **engine feature** (00n band): it defines *how* a Windows jump box is
built and is reusable across tenants/environments. It creates no resource group
and no network — those are referenced from existing infrastructure. It is a
strict sibling of `005-buildsvr` (the Linux build-server engine) and reuses the
existing `vm` naming row (no `001-naming` change required).

## User Scenarios & Testing

### User Story 1 — Operator RDP via Bastion using Entra ID (P1)

An operator needs a Windows desktop **inside** the spoke network to reach
private endpoints (e.g. resolve `privatelink` FQDNs, test private connectivity
to the services stack's private endpoints) without exposing anything publicly.

**Why this priority**: The whole point of the jump box is a secure in-network
Windows shell. Without P1 the feature delivers no value.

**Independent Test**: From the Azure Portal the operator selects the hub Bastion,
connects to the VM by name using **Entra ID** auth, and lands on a Windows
desktop; from there `nslookup <a-private-endpoint-fqdn>` resolves to a private
IP.

**Acceptance Scenarios**:

1. **Given** the VM is deployed and Bastion is healthy, **When** the operator
   clicks "Connect → Bastion → Microsoft Entra ID" on the VM, **Then** they get
   a Windows desktop (their Entra account having `Virtual Machine Administrator
   Login`).
2. **Given** the operator is on the VM, **When** they resolve a private-endpoint
   FQDN, **Then** it returns the private IP (proving private DNS line-of-sight
   from the spoke).
3. **Given** the operator tries to reach the VM directly from the public
   internet (RDP/3389), **When** the connection is attempted, **Then** it fails
   (no public IP).

---

### User Story 2 — Break-glass admin password from Key Vault (P2)

If Entra login is unavailable, an operator needs the local administrator
password to connect.

**Why this priority**: Recovery path; depends on the VM and KV existing.

**Independent Test**: An authorized operator reads the secret
`vm-<vmname>-admin-password` from the configured Key Vault and uses it as the
local admin password over Bastion.

**Acceptance Scenarios**:

1. **Given** the apply completed, **When** an authorized operator opens the
   configured Key Vault, **Then** a secret named `vm-<vmname>-admin-password`
   exists with the generated value.
2. **Given** the password is never written to tfvars/code, **When** the repo and
   plan output are inspected, **Then** the value does not appear (only the
   sensitive `random_password`/secret references do).

---

### User Story 3 — Day-2 SKU resize without redeploy churn (P3)

Operators right-size the VM without recreating the OS disk or NIC.

**Why this priority**: Lifecycle hygiene.

**Independent Test**: Change `vm_sku` in the instance tfvars one tier and
`terraform plan` shows an **in-place** VM size update (not destroy/create of OS
disk or NIC).

**Acceptance Scenarios**:

1. **Given** the VM is deployed, **When** `vm_sku` is bumped and applied,
   **Then** the VM resizes in place.

---

### Edge Cases

- **Missing subnet**: the spoke subnet must already exist (created by the vnet
  feature). The stack reads it via remote state; an empty/unknown subnet role
  fails fast.
- **Missing RG**: the target RG must already exist (created by another stack,
  e.g. services). The stack references it by name via a data source and fails
  fast with a clear error if absent.
- **Missing Key Vault**: the configured `key_vault_id` must resolve; otherwise
  plan/apply fails fast.
- **Missing log workspace**: the hub Log Analytics workspace must exist;
  diagnostic settings fail fast otherwise.
- **Public IP attempted**: any NIC config with a public IP is rejected by
  validation (WIN-INV-6).
- **Subscription drift**: provider-bound subscription must match
  `var.subscription_id` (WIN-INV-3).
- **Region drift**: region must be `swc` (WIN-INV-1).
- **KV write permission**: the apply identity must be able to write the secret.
  The engine grants itself `Key Vault Secrets Officer` on the KV and waits for
  RBAC propagation before the write (C-008-07); a transient first-apply 403 is
  resolved by re-running the apply (idempotent).

## Requirements

- **FR-801**: A single `modules/winvm/` wrapper module handles VM creation. The
  module is provider-less (Constitution VI) and sources only AVM modules for
  Azure resources (Constitution IX) — `Azure/avm-res-compute-virtualmachine/azurerm`.
- **FR-802**: A single generic root stack `terraform/winvm/` consumes the
  module. Per-deployment `(tenant, environment, region, usecase)` and the
  existing RG name, subnet role, Key Vault id are supplied via
  `variables/<tenant>/<environment>/winvm.tfvars.json`.
- **FR-803**: The root stack pins its own `subscription_id`, cross-checked at
  plan time (`check.subscription_pinned`, WIN-INV-3).
- **FR-804**: Region is allowlisted to `swedencentral` (`swc`) (WIN-INV-1).
- **FR-805**: OS = **Windows**; default image = Windows Server 2022 Datacenter
  Azure Edition (`MicrosoftWindowsServer / WindowsServer /
  2022-datacenter-azure-edition / latest`), overridable via
  `source_image_reference`. Default `vm_sku = Standard_D4s_v5` (4 vCPU, 16 GiB).
- **FR-806**: **No public IP** (WIN-INV-6). The single NIC has one ip
  configuration with a dynamic private IP in the referenced subnet. Accelerated
  networking enabled.
- **FR-807**: The VM has a **system-assigned managed identity**.
- **FR-808**: Security baseline ON by default: `encryption_at_host_enabled`,
  `secure_boot_enabled`, `vtpm_enabled` = true.
- **FR-809**: The local admin password is **generated** (`random_password`,
  length ≥ 24, all character classes) and stored as a Key Vault secret named
  `vm-<vmname>-admin-password` in the Key Vault identified by `key_vault_id`.
  The password never appears in tfvars/code/plain plan output (sensitive).
- **FR-810**: The engine grants the **apply identity**
  (`data.azurerm_client_config.current.object_id`) the `Key Vault Secrets
  Officer` role on the target Key Vault, and waits for RBAC propagation
  (`time_sleep`) before writing the secret, so the secret write succeeds from a
  fresh deployer (C-008-07).
- **FR-811**: The VM's system-assigned MI is granted `Key Vault Secrets User` on
  the target Key Vault (break-glass read).
- **FR-812**: The `AADLoginForWindows` VM extension is installed so operators
  RDP via Bastion using Entra ID; the password is break-glass only.
- **FR-813**: The engine references an **existing** resource group by name
  (`resource_group_name` input) — it creates **no** resource group and **no**
  network (Constitution: instance selects/parameterizes; engine builds the VM).
- **FR-814**: OS disk defaults to 128 GiB Premium_LRS; no data disk by default
  (jump box). Disk sizes/SKUs overridable, validated to Azure ranges.
- **FR-815**: VM + NIC diagnostic settings target the shared hub Log Analytics
  workspace (`log_workspace_resource_id`).
- **FR-816**: All resources tagged with the six-key engine baseline (tenant,
  topology/tenant, environment, region, managed_by, repo) via the naming engine.
- **FR-817**: Names come from the naming engine: RG name is referenced (existing,
  `rg_hyphenated` shape) and the VM uses the existing `vm` row (abbr `vm`,
  hyphenated) with service_purpose `jmp`. NIC / OS disk / diagnostic names are
  derived deterministically from the VM canonical name. **No `001-naming`
  change** (the `vm` row already exists).
- **FR-818**: Stable output contract: `vm_id`, `vm_name`, `vm_private_ip`,
  `resource_group_name`, `principal_id`, `admin_password_secret_id`
  (the KV secret id; not the value), `naming` passthrough.
- **FR-819**: Backend state path follows Constitution VII:
  `<tenant>/<environment>/winvm.tfstate` on the shared backend SA with
  `use_azuread_auth = true`.
- **FR-820**: CI workflow `.github/workflows/winvm.yml` mirrors `log.yml`: on PRs
  touching `terraform/winvm/**` or `modules/winvm/**`, run `terraform fmt
  -check`, `terraform validate`, and `terraform test` (with `mock_provider`).
  No live-Azure calls in CI. The `winvm` stack is added to the `deploy.yaml`
  service choice list for rollout.
- **FR-821**: Deterministic — snapshot tests on `vm_name` in the engine + stack.

## Out of scope (deferred)

- Creating the resource group, network, subnet, NSG, Bastion, or Key Vault
  (all referenced as existing).
- Data disks / app workloads (jump box is OS-disk only by default).
- GitHub Actions runner bootstrap (that is the Linux `005-buildsvr` engine's
  job; this engine is a desktop jump box, not a CI runner).
- A dedicated per-VM Key Vault with its own private endpoint (the engine reuses
  an existing private Key Vault supplied by the instance; a dedicated KV is a
  future engine option).
- Auto-shutdown schedules, backup/ASR, image gallery customization.

## Clarifications

### Session 2026-06-05

- **C-008-01** — Architecture: a **new dedicated engine** (`008-winvm`), not an
  amendment to `005-buildsvr` (which is Linux-only: cloud-init, SSH-key auth,
  hub placement). Each concrete deployment is a separate instance feature.
- **C-008-02** — Placement: the VM lands in an **existing** RG (referenced by
  name) and an **existing** spoke subnet (referenced via vnet remote state by
  role). The engine creates neither. Day-one instance: RG
  `rg-svc-uc1-sp01-dev-swc-001`, subnet role `development` (live name
  `snet-dev-vnet-net-shd-sp01-npd-swc-001`).
- **C-008-03** — Image/size: Windows Server 2022 Datacenter Azure Edition,
  `Standard_D4s_v5`. Both overridable.
- **C-008-04** — Networking: **no public IP**; RDP exclusively via the hub
  Bastion. Private-by-default mandate honored (the VM has no public surface).
- **C-008-05** — Credentials: the admin password is **Terraform-generated**
  (`random_password`) and stored in an **existing** Key Vault (no secret in
  tfvars). Day-one instance Key Vault: the existing private key vault in the
  sp01/dev services resource group (any KV id works; engine is generic).
- **C-008-06** — Login model: `AADLoginForWindows` extension + Entra ID over
  Bastion is the day-to-day path (operator holds `Virtual Machine Administrator
  Login`); the KV password is break-glass.
- **C-008-07** — KV write permission: the engine grants the **apply identity**
  (`azurerm_client_config.object_id`) `Key Vault Secrets Officer` on the KV and
  inserts a `time_sleep` for RBAC propagation before the secret write. A
  transient first-apply 403 (propagation not yet complete) is resolved by
  re-running the apply; the resources are idempotent. Documented as a known
  first-apply consideration (mirrors the services 3-pass precedent).
- **C-008-08** — Naming: reuses the existing `vm` row (service_purpose `jmp`);
  **no `001-naming` change**. RG name is referenced, not created.
- **C-008-09** — Security baseline: host encryption + secure boot + vTPM ON by
  default; system-assigned MI ON.

## Test plan

Under `terraform test` with `mock_provider` blocks — no live-Azure calls:

1. `positive_baseline.tftest.hcl` (engine + stack) — `terraform plan` succeeds;
   asserts `output.vm_name` equals the engine-emitted literal
   `vm-jmp-<usecase>-<tenant>-<environment>-swc-001` for a representative tuple.
   Doubles as the determinism snapshot (FR-821).
2. `negative_subscription_mismatch.tftest.hcl` (stack) —
   `expect_failures = [check.subscription_pinned]`.
3. `negative_disallowed_region.tftest.hcl` (stack) — `expect_failures =
   [var.region]`.
4. `negative_public_ip.tftest.hcl` (engine) — a NIC public-IP attempt is
   rejected (WIN-INV-6).
5. `negative_bad_keyvault_id.tftest.hcl` (engine) — malformed `key_vault_id`
   rejected by validation.
